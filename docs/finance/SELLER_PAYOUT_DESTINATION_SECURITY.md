# Seller payout destinations

## Current scope

Seller owners can save a bank payout destination for future settlement. The implementation is a secure destination registry plus a privileged manual review queue; it does not calculate seller payable balances or initiate transfers.

New records are always created as `PENDING_VERIFICATION`. No seller-facing or public API can set `VERIFIED`. Platform administrators can record an out-of-band ownership check with an evidence reference and reason; this is an audited human attestation, not an automated bank/provider verification. Payout execution remains disabled until independent ownership checks and the full settlement controls below are implemented.

## Data protection

- Account identifiers, account-holder names, and optional routing codes are encrypted together with AES-256-GCM.
- The database stores a fixed placeholder instead of the account-holder name in plaintext; the authenticated seller API decrypts it only for that seller.
- The authenticated seller owner may see their own decrypted account-holder name; account identifiers are never returned, and the browser receives only the account type and last four characters plus non-secret bank metadata.
- A seller-scoped HMAC fingerprint prevents duplicate registration for the same seller and settlement currency without storing a searchable plaintext account identifier.
- Fingerprint derivation is pinned to key version 1. Keep that key available for as long as any payout destination exists, including after active encryption-key rotation.
- Never log account identifiers, routing codes, encryption envelopes, or key material.
- Encryption keys must be stored outside PostgreSQL and source control.

## Ownership and defaults

Every read or mutation resolves the authenticated seller from the session and verifies an active seller account. A seller cannot address another seller's payout destination by ID.

A seller may register the same bank destination for more than one settlement currency, and may keep one default destination per currency. Database unique and partial unique indexes enforce these invariants even under concurrent requests. Disabling a destination clears its encrypted payload and removes its default status.

## Validation and verification

IBANs are checked for supported country-specific length, country prefix, and MOD-97 checksum. Local bank account entry is deliberately disabled until country-specific account and routing rules are implemented. Format validation is not proof of account ownership.

A privileged admin review queue and API now support approving or rejecting a payout destination with an external evidence reference, a review reason, actor/timestamp and an audit event. The queue exposes only masked account details and blocks self-verification. This records an out-of-band manual review; it does not itself contact a bank or provider and must not be described as automated ownership verification.

Before transfers are enabled, implement and audit:
1. Country- and rail-specific bank-detail validation for local account formats before enabling them.
2. Independent ownership verification (for example, provider verification or an approved micro-deposit flow); manual evidence review remains an operational control, not proof generated by this application.
3. Seller payable ledger postings, holds, settlement schedule, payout approval, idempotent transfer submission, webhook verification, and reconciliation.
4. A rule that only a verified destination may receive a payout.

Until those controls exist, no withdrawal or transfer API should be exposed.

## Privileged manual review endpoint

A privileged manual review command is now implemented at `POST /api/admin/seller-payout-methods/[methodId]/review`.

- Requires the global `platform:manage` permission and the platform step-up/MFA policy.
- Accepts only `VERIFIED` or `REJECTED`, a non-empty external evidence reference, and a reason.
- Rejects self-review when the platform actor is also the seller owner.
- Reviews only `PENDING_VERIFICATION` records; repeat or conflicting reviews return a conflict.
- Each review is bound to the exact `updatedAt` snapshot returned by the queue. Disable/re-registration changes this timestamp; stale evidence is rejected even if the database row ID is reused. The write also checks the expected timestamp and pending status atomically.
- Updates the destination status and audit record in one serializable transaction.
- Stores the evidence reference and reason in the audit metadata, never the account identifier or encrypted payload.
- A rejection clears the default flag. A successful manual review records `verifiedAt`.

This endpoint records an administrator's attestation after an out-of-band check with the bank or an approved verification provider. It does **not** contact a bank, validate account ownership automatically, initiate a payout, or make a seller balance withdrawable. The admin review UI submits the exact queue snapshot timestamp with every decision. Do not review a destination as verified without independently confirming ownership through an approved channel.
